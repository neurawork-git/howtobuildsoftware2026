## Summary

Added a third engine — `compliance-compiler` — to the `neurawork-cc-harness` plugin,
self-hosted in this repo as `compliance-base/` (mirroring `knowledge-base/` and
`claudemd-lerner/`). It (1) extracts GDPR/SOC2/ISO27001 into a repo-tracked constraint
catalog via ~30 parallel Claude Agent SDK agents, and (2) validates PRP plan files
against that catalog through a new `PostToolUse` hook (inline structural precheck +
detached deep LLM report). Plan-only design was executed end-to-end; the extraction
itself is operator-run (needs an API key).

## Deviations from Plan

1. **34 shards, not "~30".** GDPR 10 + SOC2 13 + ISO27001 11. The plan targeted ~30
   (test range [27,33]); the SOC2 split to one-shard-per-Common-Criterion (CC1–CC9)
   plus the four trust categories naturally yields 13. Test range widened to [28,40].
   More parallelism, in line with the user's "as parallel as possible".
2. **plugin.json: description-only edit.** The plan listed a plugin.json UPDATE to
   "register" the skill/commands. The manifest does not enumerate skills/commands
   (they are auto-discovered from `skills/` and `commands/` dirs — the existing two
   engines aren't listed either), so registration needed no structural change; only
   the human-readable description was updated to mention the third engine.

---

## Issues Encountered

- **Ruff E402 in hooks/install/recon**: the sys.path-then-import pattern is a runtime
  requirement (payload resolves siblings + `_shared` at `uv run` time). The two
  existing engines exhibit the identical E402 baseline without `# noqa`. Chose to
  match that established style rather than diverge; documented rather than silenced.
- **PostToolUse payload shape** (flagged as the plan's top open risk): no example
  existed in-repo. Parsed defensively (`tool_name`, `tool_input.file_path`/`path`),
  smoke-tested with synthetic stdin for Write-to-plan, non-plan write, and Read.
